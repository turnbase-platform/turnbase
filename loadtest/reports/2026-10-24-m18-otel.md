# OpenTelemetry agent cost (`parallelism` under three agent configurations), `IMP-M18-06`, 2026-10-24

**Verdict:** On the platform at `9eb9738` (IMP-M18-03 to 05 in) the agent as specified costs 2.20 ms of platform CPU per move; with the JDBC and Lettuce modules off it is 1.99 ms (-9%), with the agent off 1.81 ms (-18%). The ceiling of `parallelism` moves from 192 pairs (agent as specified) to 224 (JDBC and Lettuce off) to 256 (agent off); the first to break is the DB pool in all three. **The owner chooses; nothing is changed until then.** Single-node, laptop result.

## 8. Findings

- The agent costs 18% of the platform's CPU per move at the baseline (2.201 to 1.813 ms); the JDBC and Lettuce modules alone are about half of that (9.4%). M16 measured 19 to 20% by profile; this is the same figure by direct comparison.
- The saving shows up as ceiling (192 to 224 to 256 pairs), not as peak moves/s, which is 2,056 to 2,212 in all three: the Game Host at 2 cores and the 10-connection pool bound the throughput. Peak moves/s of configuration 2 (2,056) is below configuration 1's (2,161); the steps are single runs on a laptop, with a spread of several percent, and the 192 to 288-pair steps of configuration 2 (1,763 to 1,808) are low enough to be a lower Game Host state (1.88 to 1.91 cores of 2) rather than a real effect of the setting.
- Platform CPU per move is 2.20 ms against M16's 2.60 ms: IMP-M18-03 to 05 cut 15% with the agent unchanged.
- One run per configuration and level; differences under about 5% are noise (`2026-10-21-m16-cpu.md` §1).

## 9. Constants

- This is a single-node, laptop ceiling: Docker Desktop Kubernetes on one WSL2 VM shared with the load generator. It is the ceiling of this machine, not of the platform.
- Latency is measured per request from a closed-loop client at the configured think time, so coordinated omission applies: when the system slows, the client issues fewer requests and the percentiles understate the delay a constant-rate client would see. `start-rate` is open-loop.
- One step is generator-bound when the k6 process averages more than 80% of its pinned cores after the settle window; such a step never counts as the platform's breaking point.
- The first `SETTLE_SECONDS` of every step are excluded from that step's thresholds.
- A crossed threshold aborts the run no earlier than 30 s after the test start (`delayAbortEval` counts from the test start, not from the step), so a step's first samples after its settle window can trip a one-sample percentile.
