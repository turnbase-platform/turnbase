## 5. Result

Ceiling (pairs): 70 (load used: 49 = 70 x 7 / 10; the scenario is not a search for a ceiling)
First to break: none
Evidence: no threshold crossed, no restart, no OOM kill in attempt 2. Resources tied to a connection (sockets, rooms, sessions, Hikari connections) returned to their starting value of 0 within 30 s of the last pair leaving; resources the platform keeps in process or in Redis did not (§6, §8).

`Ceiling (pairs)` is one integer: the last step all of whose thresholds passed and that is not
generator-bound, or `<n> (not reached)` when no step failed. `First to break` is exactly one of:
`Game Host CPU`, `Espresso contention`, `DB pool`, `Redis`, `platform threads`, `ingress / frontend nginx`,
`k6 itself`, `memory (OOM)`, `none`. A report for `start-rate` writes `Ceiling (games/s): <n>` instead.

## 8. Findings

- **Attempt 1 was lost to a Game Host wedge on its first cold start, with the default single context.** Run `20261018-234603-up-down-attempt1`: scenario start 21:46:17Z, `Game context created` 21:46:24Z, then `BootWatchdog` at 21:46:44Z ("Guest boot wedged ... still running after 20000 ms; taking this host out of service"). The supervisor then logged "the JVM has not answered 4 probes in a row; killing it", and the new JVM logged its first line at 21:52:39Z, so no game could start for about 6 minutes (platform CPU 0.10 cores in the first 300 s, 1 Game Host restart, one `tb_game_start` of 59 s, 278 errors, platform heap up to 1.4 GB, HTTP p99 up to 2 s and 5xx 0.06/s in the second segment). It is the same wedge as `load-testing.md` §13 item 7, which was seen with four contexts: it is not specific to them, and this time the supervisor did kill the JVM. Attempt 2, run on a freshly reset stack, did not wedge. Not checked: the wedge's frequency (the supervisor script says roughly one cold boot in ten deadlocks), why the kill took about 6 minutes.
- **Redis keeps two keys per room forever.** 18,021 rooms created, 36,047 keys and 6.91 MB at the end, no key removed after the rooms closed (`room:<id>:pod`, `room:<id>:epoch`); the same pattern gave 86,271 keys and 13.9 MB in the 30-minute `soak` (`2026-10-18-soak.md`). Memory per room is about 0.29 KB. Suspected cause: ownership keys without TTL or a delete on room close. Not checked: whether a TTL is set, what the reconciliation job removes.
- **The platform keeps 109 threads at zero load** (57 before, 131 at the peak): it dropped from 129 to 110 at 970 s (70 s after the last pair left) and stayed at 109 to 110 for the next 220 s. Suspected cause: a pool that shrinks once, not to its core size. Not checked: which pool, a longer idle wait.
- **The Game Host heap used rises at zero load** (285 MB at 930 s to 317 MB at 1,170 s) because no GC ran; not a leak on this evidence. Not checked: a forced GC.
- **`connected_clients` is 5 after the run against 4 before.** Suspected cause: one additional connection opened under load and kept. Not checked: which client.
- **Errors by code were not recorded** (§7): the Prometheus series was empty for this run. The 11 errors are 0.001% of operations.
- **Harness note.** The Redis figures over time come from a 30 s side loop (`kubectl exec ... redis-cli INFO`, in `/tmp`), not from `loadtest/`; `snapshot.sh` reads Redis once at the end.

## 9. Constants

- This is a single-node, laptop ceiling: Docker Desktop Kubernetes on one WSL2 VM shared with the load generator. It is the ceiling of this machine, not of the platform.
- Latency is measured per request from a closed-loop client at the configured think time, so coordinated omission applies: when the system slows, the client issues fewer requests and the percentiles understate the delay a constant-rate client would see. `start-rate` is open-loop.
- One step is generator-bound when the k6 process averages more than 80% of its pinned cores after the settle window; such a step never counts as the platform's breaking point.
- The first `SETTLE_SECONDS` of every step are excluded from that step's thresholds.
- A crossed threshold aborts the run no earlier than 30 s after the test start (`delayAbortEval` counts from the test start, not from the step), so a step's first samples after its settle window can trip a one-sample percentile.
