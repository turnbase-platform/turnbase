# Contexts scenario report, 2026-10-18

**Verdict:** Four copies of Tic-Tac-Toe over 50 pairs ran clean for 5 min (810 moves/s, move p95 58 ms, warm game start p95 66 ms) but cost the Game Host about three times the CPU of one context for the same throughput, and the first attempt wedged the Game Host on its first game start with nothing restarting it. Single-node, laptop result.

## 5. Result

Ceiling (pairs): 50 (not a ceiling: the scenario runs one fixed load of 50 pairs and finds none)
First to break: none
Evidence: at the same 810 moves/s as the single-context run, with four game ids the Game Host used about three times the CPU (2.95 against 0.99 cores) and twice the heap (0.8 GB against 0.4 GB); the latencies were the same at the median (36 ms) and
slightly worse in the tail (move p95 58 against 46 ms, p99 85 against 54 ms; game start p95 66 against 55 ms). Against `parallelism` (one game id; 909 moves/s at 32 pairs and 897 at 64) the 810 moves/s of four contexts is about 10% lower, not a collapse. Throughput was about the same because the platform pod, at 2.4 to 2.7 of 4 cores, is what limits both runs (`ramp-to-break`: about 3 cores from 20 pairs on).
The Game Host was not the limit: 3.0 of 4 cores, no `dispatch` error, no 5xx, no restart, `hikari_pending` 0, Postgres 1.33 of 2 cores, Redis 0.34 of 1. The extra Game Host CPU is the context cost the scenario was built to expose; it is not explained here (see section 8), and with a limit of 4 cores it leaves
headroom of one core, so a larger number of contexts would be the next thing to try. The first game start on a cold Game Host took 10.2 to 10.3 s for all 50 pairs, about twice the 5 s seen with a single context in `start-rate` and `default-limits`.

Capacity statements:

- 500 concurrent sessions: **not attempted** (peak `sessions_active` 41).
- 5,000 WebSockets: **not attempted** (peak 100 open).

## 8. Findings

- **Attempt 1 failed because the Game Host wedged on its first game start, and nothing restarted it.** Under `contexts` attempt 1 (same parameters, `20261018-223428-contexts-attempt1`, k6 exit 99) no game started in 357 s: `tb_game_start` 0 samples, `tb_games_completed` 0, 584 iterations ended in 148 `ready_timeout`, 284 `connect_timeout` and 152 `ws_closed`,
  `http_req_failed` 5.3%, `ws_connecting` p99 9.7 s. The evidence for the cause is four pieces: the platform log has `DEADLINE_EXCEEDED` on `CreateSession`; the Game Host log has the `BootWatchdog` line (ADR-0018 §2: 20 s boot timeout); `/actuator/health` answered 503 while the process stayed up and
  the pod was never restarted; and `supervise.sh` counts any HTTP answer, a 503 included, as alive, so the supervisor never killed it. In the wedged pod there was no `kill` binary (only the shell builtin) and `jcmd` could not attach; `kill -3` from `sh -c` produced no thread dump. (Corrected by IMP-M16-01: the original text said the image has no `jcmd`; `/usr/bin/jcmd` exists, and it is the wedged JVM that does not answer.) So the host was in the state ADR-0018 describes as `HostWedge` (health DOWN) without the exit
  with code 70 that should follow, and the supervisor, by design, does not act on that state. This is a result, not a harness fault (the harness only drives the pairs); the stack was reset and the scenario rerun once (attempt 2, this report). The observed frequency is one wedge in two cold starts with four contexts;
  ADR-0018 gives one in four for the single-context boot. Not checked: whether the wedge is in the first context's boot or in the creation of a second context, whether the 20 s `BootWatchdog` expiry is simply too short for four contexts started at once (attempt 2's cold start took 10.3 s), and the exact log lines (the pod's logs were lost when the stack was reset).
- **Cold start with four contexts: 10.2 to 10.3 s for all 50 pairs, about twice the single-context 5 s.** The 50 cold-tagged starts are within 0.1 s of each other, so they waited on one shared event, not on 50 separate ones; that the four contexts were created one after another (about 2.5 s each) or competed for the same CPU is a guess. The ratio puts the cold start at half the 20 s `BootWatchdog` limit.
- **Four contexts cost about three times the Game Host CPU for the same moves per second.** 2.95 against 0.99 cores at 810 against 812 moves/s, heap 0.8 against 0.4 GB, with the same median latency. Candidate causes, none checked: per-context JIT compilation that is not shared (Truffle compiler threads), a warm-up that continues for the whole 5 minutes (the CPU is flat across the three segments, so it does not look like warm-up), per-context isolation overhead on each call. Not checked: a thread dump or profile at the plateau, the same 50 pairs on one context in the same session. That the four contexts were live is inferred from `CONTEXT_IDS` and the pair-to-id assignment; the `Game context created` log lines were lost with the reset.
- **The platform, not the Game Host, set the throughput**, as in `ramp-to-break`: 2.4 to 2.7 of 4 cores at 810 moves/s, flat latency, no queueing in the pool.
- A 10 s WebSocket connect (`ws_connecting` max 10.0 s, the harness connect timeout) occurred at least once in this run (its count is not exposed), also seen in `start-rate` (see its section 8): the cause is undetermined.
- No restart, no `OOMKilled`, no 5xx, generator never bound.

## 9. Constants

- This is a single-node, laptop ceiling: Docker Desktop Kubernetes on one WSL2 VM shared with the load generator. It is the ceiling of this machine, not of the platform.
- Latency is measured per request from a closed-loop client at the configured think time, so coordinated omission applies: when the system slows, the client issues fewer requests and the percentiles understate the delay a constant-rate client would see. `start-rate` is open-loop.
- One step is generator-bound when the k6 process averages more than 80% of its pinned cores after the settle window; such a step never counts as the platform's breaking point.
- The first `SETTLE_SECONDS` of every step are excluded from that step's thresholds.
- A crossed threshold aborts the run no earlier than 30 s after the test start (`delayAbortEval` counts from the test start, not from the step), so a step's first samples after its settle window can trip a one-sample percentile.
