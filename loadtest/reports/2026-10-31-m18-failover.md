## 8. Findings

- **A Game Host SIGKILL loses games; the other three kills do not.** Kill times (UTC) and watched games lost: Platform SIGKILL 17:44:22, 0; Game Host SIGKILL 17:46:41, 4; Platform graceful 17:48:53, 1; Game Host graceful 17:51:10, 0. The Game Host SIGKILL took the in-memory game sessions of that pod with it: two clients waited for a frame and timed out (`sync_timeout`) and two exhausted the reconnect budget (`retry_budget`). Whether the platform is meant to recreate a session from its stored state is a question for the Game Host recovery design; this run measures that it did not within the harness's budget.
- **The graceful Platform delete lost one game after 36 s**, on `retry_budget`, with the replacement Ready 25 s after the delete. The watched pair's reconnect used the stale instance hint for longer than the budget; the SIGKILL of a Platform pod two minutes earlier lost none.
- **Recovery time is within the bound where it completed.** Six recoveries timed (nine counted): median 0.1 s, p95 and max 20.8 s, against NFR-ASC-007's 30 s.
- **Replacement pods were Ready fast:** Platform 26 s (SIGKILL) and 25 s (graceful), Game Host 19 s and 20 s.
- **Correctness otherwise held:** 0 sequence gaps and 0 duplicates over 3.27 million broadcast events and no room left `IN_PROGRESS`. `FAIL games` is the harness count: 214,223 started against 214,205 completed and 17 abandoned (one game neither), the 1 `tb_si_games_aborted`.
- **No autoscaling event beyond the first minute:** the Platform went 2 to 3 at +54 s (Ready +75 s) (setup login burst) and stayed; the Game Host stayed at 2 except for the killed replicas' replacement.
- **Slew:** the wall clock ran 6.3% slow.

## 9. Constants

- This is a single-node, laptop ceiling: Docker Desktop Kubernetes on one WSL2 VM shared with the load generator. It is the ceiling of this machine, not of the platform.
- Latency is measured per request from a closed-loop client at the configured think time, so coordinated omission applies: when the system slows, the client issues fewer requests and the percentiles understate the delay a constant-rate client would see. `start-rate` is open-loop.
- One step is generator-bound when the k6 process averages more than 80% of its pinned cores after the settle window; such a step never counts as the platform's breaking point.
- The first `SETTLE_SECONDS` of every step are excluded from that step's thresholds.
- A crossed threshold aborts the run no earlier than 30 s after the test start (`delayAbortEval` counts from the test start, not from the step), so a step's first samples after its settle window can trip a one-sample percentile.
