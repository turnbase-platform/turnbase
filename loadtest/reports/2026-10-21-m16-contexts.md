# Contexts scenario report, 2026-10-21

**Verdict:** Four copies of Tic-Tac-Toe over 50 pairs ran clean for 5 min with 0 errors (845 moves/s, move p95 79 ms, warm game start p95 93 ms), but the Game Host still used about 3.0 cores, three times the 0.93 it uses for one context at the same pair count, and the cold start took 21.3 s on average (max 27.8 s) against 10.2 s in Phase A. The shared Espresso engine of `IMP-M16-05` did not change the CPU cost of four contexts; the 10 s WebSocket stall and the `ready_timeout` errors of Phase A did not occur. Single-node, laptop result.

## 5. Result

Four contexts are not a capacity limit at 50 pairs on this machine: no threshold is close, nothing failed, and the platform (2.2 to 2.9 cores) and Postgres (1.49 of 2 cores, Redis 0.42 of 1) have headroom. The cost is in the Game Host: 2.83 to 2.98 cores of 4 in every segment (3.0 to 3.6 cores by minute from `pods.csv`), against 0.93 for the same 50 pairs on one context. The scenario does not search for a breaking point, so it has no ceiling or first-to-break line of its own.

Ceiling (pairs): 50 (not reached)
First to break: none
Evidence: nothing broke in 5 minutes at 50 pairs (0 errors, every threshold with margin, no restart, no 5xx). The Game Host at about 3 of its 4 cores is the nearest limit, with about one core of headroom, so more contexts or more pairs would reach Game Host CPU first; this run did not test that.

`Ceiling (pairs)` is one integer: the last step all of whose thresholds passed and that is not
generator-bound, or `<n> (not reached)` when no step failed. `First to break` is exactly one of:
`Game Host CPU`, `Espresso contention`, `DB pool`, `Redis`, `platform threads`, `ingress / frontend nginx`,
`k6 itself`, `memory (OOM)`, `none`. A report for `start-rate` writes `Ceiling (games/s): <n>` instead.

## 8. Findings

- **Finding 9 persists unchanged.** Four contexts cost the Game Host 2.83 to 2.98 cores at 845 moves/s (2.95 to 3.03 at 810 in Phase A), against 0.93 cores at 1,012 moves/s for one context at 50 pairs in the `ramp-to-break` of this session. Median move 26 ms and p95 79 ms (36 and 58 in Phase A); p99 140 ms (85). The cost is flat over the 5 minutes (3.0, 3.6, 3.1, 3.1 and 3.1 cores per minute), so it is not warm-up. The shared Espresso engine of `IMP-M16-05` did not reduce it. Heap is 0.53 to 0.68 GB (0.8 in Phase A). Not checked: a profile of the four-context plateau, one context at the same pair count in the same session, whether code is shared between contexts of different bundles.
- **Finding 8 is worse, not better: the cold start takes 21.3 s on average (50 starts, max 27.8 s), against 10.2 s to 10.3 s in Phase A.** The four contexts are created within the same millisecond, so creation is concurrent, and the boot that follows is the cost. Since `IMP-M16-03` the warm-up context is off by default, which moves the first guest boot into the first real game starts; that is the likely reason and was not isolated. The mean is above the 20 s of the boot limit, yet no `BootWatchdog` line and no error appeared. Not checked: the cold start of one context with the warm-up off in the same session, whether the 20 s limit counts from the guest boot and not from the platform's request, a rerun with the warm-up on.
- **Finding 7 (the wedge) did not occur** in one cold start with four contexts (Phase A: one in two); a single cold start is no frequency, which `IMP-M16-03` measured (2 of 40 with the warm-up off).
- **Finding 4 is resolved here:** 0 errors in 33,175 games and 253,564 moves (6 `ready_timeout` in Phase A). **Finding 10 did not occur:** `ws_connecting` max 367 ms over 13,270 connects (10.0 s in Phase A) and `http_req_duration` max 480 ms.
- No restart, no `OOMKilled`, no 5xx, no generator-bound segment. Game Host threads 100 to 124 (52 in Phase A); platform threads 164 to 193.

## 10. Constants

- This is a single-node, laptop ceiling: Docker Desktop Kubernetes on one WSL2 VM shared with the load generator. It is the ceiling of this machine, not of the platform.
- Latency is measured per request from a closed-loop client at the configured think time, so coordinated omission applies: when the system slows, the client issues fewer requests and the percentiles understate the delay a constant-rate client would see. `start-rate` is open-loop.
- One step is generator-bound when the k6 process averages more than 80% of its pinned cores after the settle window; such a step never counts as the platform's breaking point.
- The first `SETTLE_SECONDS` of every step are excluded from that step's thresholds.
- A crossed threshold aborts the run no earlier than 30 s after the test start (`delayAbortEval` counts from the test start, not from the step), so a step's first samples after its settle window can trip a one-sample percentile.
