# M16 platform CPU per move, 2026-10-21

**Verdict:** There is no hotspot of 10% or more with a local fix. The platform spends 2.60 ms of CPU per move, spread over the OpenTelemetry agent (about 19%), the JDBC stack (about 19%), the STOMP channels (about 13%), Lettuce (about 10%) and gRPC (about 7.5%). Two local defects were fixed (the hot-row lock on `game`, and a disconnect scan that was linear in every room ever served); the second is gone from the profile (2.3% to 0.0%), neither changes CPU per move (2.604 ms before and after) or moves per second (1,258 before, 1,212 after, inside run-to-run spread), and Hikari wait halved (pending mean 26.3 to 13.2).

## 3. Statements and commands per move and per join

Counters from the smoke run `loadtest/results/20261021-185140-smoke`: `pg_stat_statements` for the whole run (zeroed by `run.sh start`; about 11,200 moves and 3 games), Redis from a 58 s `MONITOR` sample inside it (23 moves, so the Redis ratios are approximate). Per move:

| Store | Per move | What |
|---|---|---|
| Postgres | 3.8 | `select host_user_id from room` 1.26, `select connection_count > 0 from room_participant` 1.26, `select user_id from room_participant ... connection_count > 0` 1.26 (14,112 to 14,116 calls each); no write, no transaction |
| Redis | about 10 | `GET session:` 1.26, `GET routing:` 1.26, `SET session:`, `SET delivered:`, `SET failcount:`, `RPUSH gamelog:`, `PEXPIRE gamelog:` 1 each, `INCR seq:` and `GET delivered:` 0.87 each |

The two `room_participant` lookups and the host lookup answer the same question per move (is this user the acting participant of a live room) and are the first candidates for a per-room cache in Phase B; a cache is an invalidation design (join, leave, disconnect, kick), not a local fix.

Per game (completion): `insert into game_session_completion`, `update game set completed_session_count`, `insert into game_history_entry` once per participant, `delete from game_input_outbox`, `insert into session_teardown` / `delete from session_teardown`: 3 calls each in the 3-game sample. Per room join: `select ... for update` on the participant, `insert into room_participant` with a `select max(join_order)`, the team-slot query (`room_team` left join `room_participant`, 2.6 ms mean in the sample, the slowest per-join statement), the `room` version CAS, and the invitation delete.

## 4. Fixes

| | Defect | Fix | Test |
|---|---|---|---|
| F1 | `HistoryRecordingService.record` executed `update game set completed_session_count = completed_session_count + 1` first, so the row lock on the game's single `game` row was held for the rest of the transaction (history entries, up to a 3.8 ms statement at 64 pairs, almost all lock wait) and every completion of that game queued behind it | The increment is the last statement of the transaction; the lock is held only until the commit. `data-model-history.md` §3 says so | `HistoryRecordingServiceTest` (4 tests, Mockito `InOrder`: increment after the completion insert and after the entries; not at all when the insert was a duplicate; entries skipped on a null roster or an invalid outcome still count the game) |
| F2 | `RoomSubscriptionAuthorizer.onSessionDisconnect` walked every room the instance had ever served on each disconnect (`O(rooms)`, 2.3% of platform CPU at 64 pairs, growing with uptime) and never removed a room's empty session set | A session-to-rooms index (`roomsBySession`) is kept beside `sessionsByRoom`; a disconnect touches only that session's rooms and prunes empty sets; `onRoomOwnershipLost` uses the same helpers | Three tests in `RoomSubscriptionAuthorizerTest` (a disconnect leaves no room behind, a room keeps its other sessions, a session in two rooms is forgotten in both); `trackedRooms()` and `trackedSessions()` expose the sizes |

F1 did not change throughput measurably: the game-row statement was not the limit at this load (3 calls in the smoke; about 140 completions per second at 64 pairs, each a row lock held for microseconds once the entries are no longer inside it). It removes a serialisation point that would appear with a hotter single game.

## 5. Phase B notes (recorded in `load-testing.md` §13 findings 1 and 2)

1. **The OTel agent is 19 to 20% of platform CPU.** Options: head sampling of the move path (the spans of `GameInputService` are per move), disabling the JDBC and Lettuce instrumentation modules, or a manual SDK. Each changes `observability.md` §4 or `FR-TRACE-001`. An experiment with `OTEL_JAVAAGENT_ENABLED=false` was not run in this item.
2. **Per-move reads are 3.8 statements and 10 Redis commands.** A per-room participant cache and one Redis round trip (a pipeline or one Lua call) for the `session`/`delivered`/`failcount`/`gamelog` writes would remove most of the JDBC and Lettuce share (about 29% together). An architecture change.
3. **The pool of 10 connections is saturated at 64 pairs** (pending max 62 to 68). Raising it moves the limit to Postgres (1.6 to 1.8 of its 2 cores, finding 1).
4. **STOMP fan-out is 12 to 13% of CPU**, mostly `MessageHeaders` copies per subscriber; the simple broker does not share a serialised frame between subscribers.

## 7. Reproduce

`bash loadtest/install.sh` with the JFR flags above, `reset.sh`, `provision.js`, `run.sh start parallelism K6_CORES=4 LEVELS=64 STEP_SECONDS=240 SETTLE_SECONDS=30`, `run.sh wait`, `steps-table.sh <run>/summary.json`, `snapshot.sh <run> 240`, `cpu-per-move.sh <run>`. After the run, `kubectl cp <platform pod>:/tmp/jfr <dir>`, then `jfr print --events jdk.ExecutionSample --stack-depth 40` per chunk (`jfr assemble` produced a file `jfr print` could not read: "locked stream state"; the chunks are readable).
