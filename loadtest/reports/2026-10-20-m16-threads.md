## 4. What retained the threads, and what was done

- **Tomcat workers (`http-nio-8080-exec`): 22 before, 39 at the peak and still 39 five minutes after the load (run A).** Not a leak: with the Game Host scaled to zero the pool shrank to its floor, so something was keeping the workers warm. Tomcat releases a worker above `min-spare` only after 60 s idle, and its waiting workers are served in turn; the Game Host's heartbeats and registry calls (about 0.5 requests per second) hand a request to each in turn, so none idles for 60 s. Fixed by `TomcatWorkerIdleTimeout` (10 s idle time on the worker pool) and explicit `server.tomcat.threads.max: 200` and `min-spare: 10`; run C: 21, 60, 20.
- **`grpc-default-worker`: 4 threads at the peak that stayed (run A).** gRPC's default event loop is sized from the processors and not released. `GameHostChannels` now gives every channel one shared two-thread event loop (`grpc-client-worker`) and one bounded call executor (core = processors, maximum 4 x processors, 60 s keep-alive, core threads included).
- **The STOMP channels were not on a pool of their own.** Spring Boot's WebSocket configurer (order 0) hands both channels the context's one `AsyncTaskExecutor`, and run A's peak census shows 8 threads each under the `clientInboundCh` and `clientOutboundC` names. `WebSocketConfig` now sets an executor per channel with `executor(...)`, which wins over Boot's because the platform's configurer runs after it: core = processors, maximum 4 x processors, 60 s keep-alive with `allowCoreThreadTimeOut`, caller-runs rejection. The broker channel has no executor with the simple broker (no `brokerChannel-` thread appears), so it is left as it is; giving it a pool would add a hand-off to every fan-out.
- **`spring.task.scheduling.pool.size` was ignored.** Boot builds its `taskScheduler` only when the context has no other `TaskScheduler`, and the WebSocket broker always contributes `messageBrokerTaskScheduler` , so the `@Scheduled` jobs ran on that. `SchedulingPoolConfig` defines the `taskScheduler` bean from Boot's builder, so the property (4) now applies and the jobs run on `scheduling-` threads.
- **Run B showed that a queue costs throughput.** With a 1,000-frame queue in front of 4 core threads the pools never grew (a thread pool grows past its core only when the queue refuses a task) and the inbound handlers, which block on the Game Host, were capped at four concurrent calls: move round trip p50 25 ms to 43 ms, platform CPU 2.3 to 1.9 cores. Run C replaced the queue with a hand-off (`SynchronousQueue`): the pools grow to 16 each at the peak (the 156 threads) and release them: both prefixes are gone from the `after` census.
- Not changed: `lettuce-nioEventLoop` (2 before, 3 at the peak, 4 after; Netty's event loops, no cost worth a custom client resources bean), the Hikari and JDBC helper threads (1 each).

## 5. Verdict on the Done-when clause

Run C: idle after = 81, idle before = 77, difference 4 (limit: the larger of 10% = 7.7 and 10 threads). Met after one fix cycle (B was the intermediate, C the repeat).

## 6. Open observation

Run C recorded 17 `ready_timeout` errors (`prom/errors-by-code.txt`; 17 of 256,414 operations, 0.007%, under the 1% gate) and p99 move round trip 63 ms against 45 ms in run A, while p50 and p95 improved. Runs A and B had none. One run each; the platform log of run C was not kept, so the cause (the hand-off pools admitting more concurrency than before, or noise from the shared VM) is not established. Re-measure in `IMP-M16-14` with the platform log kept before treating either as a regression.
