## Prioritized gaps

### BLOCKERS — must be decided before any deploy exists

1. **Cloud provider and K8s flavor are literally "TBD"** (CON-011). Everything else hangs off this. **Default:** AWS, EKS. **Critical wrinkle:** FR-SEC-001 makes gVisor a *Must*, and EKS has no managed gVisor support — it requires a dedicated node group with a custom AMI/bootstrap installing `runsc` plus a `RuntimeClass`. GKE Sandbox offers gVisor as a checkbox. Options: accept the EKS custom-node work, explicitly defer gVisor for MVP (Truffle remains as the isolation layer — this weakens FR-SEC-005's two-layer claim and should be a recorded risk decision), or pick GKE for this reason alone. Deserves its own short ADR.
2. **No IaC at all.** **Default:** Terraform (or OpenTofu) in a new `turnbase-infra` repo: VPC, EKS, ECR, RDS, ElastiCache, S3, Route53, ACM, IAM/IRSA. One workspace per environment.
3. **No database operational decision.** PostgreSQL is named but nothing about how it runs. **Default:** RDS PostgreSQL single-AZ (MVP) with automated backups + 7-day PITR; **Flyway** for schema migrations, run as an init step/Job before rollout, with a backward-compatible-migrations rule so rolling deploys are safe. Nothing about migrations exists in any doc today — this is a day-one implementation need.
4. **Redis durability contradiction.** The architecture makes Redis the *sole* crash-recovery layer for live game state (FR-FAIL-004, FR-SESS-003a) and OQ-001 resolves to a *single* Redis instance — yet no persistence/HA requirement exists for Redis itself. If that pod/node dies, every active game is lost, which FR-FAIL-002's recovery story silently assumes cannot happen. **Default:** ElastiCache for Redis with one replica + Multi-AZ failover for MVP, plus an explicit written statement of the accepted loss window.
5. **Runtime secrets and per-env config.** **Default:** AWS Secrets Manager + External Secrets Operator into K8s Secrets; Spring profiles per env via ConfigMaps; JWT signing keys in Secrets Manager with a documented manual rotation procedure (automated rotation post-MVP).
6. **Ingress/TLS/WebSocket path is undefined** while the product is WebSocket + SSE centric. **Default:** AWS Load Balancer Controller with ALB ingress, ACM certs, Route53 DNS; ALB idle timeout raised above the STOMP heartbeat interval (the 60s default will kill quiet connections); target deregistration delay + Spring Boot graceful shutdown + `preStop` hook so deploys drain WebSocket connections instead of dropping 5k of them. NFR-SCALE-001 already removes sticky-session needs via Redis pub/sub — the right call — but drain-on-deploy behavior still needs specifying.

### IMPORTANT — should be written down before implementation; won't stop a first deploy

7. **Deploy mechanism and rollout strategy.** The tag-based trigger exists but nothing says *what* applies manifests. **Default:** Helm chart per deployable, `helm upgrade --wait` from GitHub Actions with OIDC-to-AWS (no long-lived keys); rolling update with `maxUnavailable: 0`; rollback = `helm rollback` or re-tag (FR-CICD-008 anticipates this). GitOps/ArgoCD post-MVP.
8. **No staging environment.** CON-011 defines exactly local and prod. Either add a cheap near-zero-scaled staging from the same Terraform, or record the decision to skip it and rely on post-merge E2E (OQ-002) plus post-deploy smoke tests as the promotion gate.
9. **Production observability stack deployment.** OQ-003 covers Docker Compose only. **Default:** kube-prometheus-stack + Loki + Tempo via Helm, single-replica, S3-backed with aggressive retention (metrics 15d, logs 14d, traces 3d) — fits the stated learning goal; Grafana Cloud free tier is the cheaper fallback. Add one external uptime check (UptimeRobot/healthchecks.io) since self-hosted monitoring cannot report its own cluster being down, which NFR-OBS-001 implicitly requires.
10. **Security scanning is entirely absent from CI.** **Default:** Dependabot (also solves the missing dependency-update strategy) + Trivy image scan on the merge-to-main image build; fail on critical CVEs.
11. **Frontend deployment shape undecided** — CLAUDE.md says "Docker image / static assets", and FR-CICD-001 forgets the frontend repo has a pipeline at all. **Default:** S3 + CloudFront for static assets (cheaper and simpler than a container), which also gives a natural CDN/WAF attachment point; extend FR-CICD-001 to all component repos.
12. **Cost ceiling and SLO realism.** Nothing acknowledges cost; the honest MVP floor for this architecture (EKS control plane, 2–3 nodes incl. a gVisor node, RDS, ElastiCache, ALB, NAT) is roughly $250–400/month. Write a budget, and downgrade NFR-AVAIL-001's 99.9% (≤43 min downtime/month — not achievable solo without on-call) to a stated aspiration with a realistic 99% MVP target.
13. **GDPR / user data deletion.** Retention rules exist but there is no account-deletion/erasure flow, and FR-RET-003 keeps game history forever. For a public EU-reachable deployment this needs at least a requirements-level answer (e.g., pseudonymize history records on account deletion).

### MINOR

14. **DDoS/WAF:** app-level rate limiting (Bucket4j + Redis) is specced; edge protection isn't. AWS Shield Standard is free; WAF can wait.
15. **ADR practice:** `docs/superpowers/specs/` already functions as design records — formalize it as the ADR home in CLAUDE.md.
16. **Submodule ref bumps:** repo-strategy says refs update after green builds but nothing automates it; a small scheduled workflow or a documented manual step suffices.
17. **NetworkPolicies for the platform tier** (only Game Host egress is specified) and image signing — fine to defer, but record the deferral.
18. **Alert receiver** (FR-ALERT-005 leaves it open): pick Slack webhook via Alertmanager and move on.

## Verdict

The requirements are strong on *application-level* operability (logging, metrics, tracing, alert rules, CI test gates, scheduled jobs, retention) and the repo/branching/versioning strategy is already written and sensible — but nearly everything between "Docker image exists" and "users can reach it over TLS" is explicitly declared Out of Scope and decided nowhere: provider, IaC, ingress/TLS, registry, database operations and migrations, Redis durability, runtime secrets, and the production observability deployment. Before implementation starts, three new docs would close the gap: **(1) a deployment & infrastructure spec** (AWS/EKS decision incl. the gVisor-on-EKS trade-off ADR, Terraform layout, ECR, ALB/ACM/Route53, environment list, Helm-based deploy flow, WebSocket draining, rollback), **(2) a data-operations spec** (RDS + backup/RPO-RTO, Flyway migration workflow compatible with rolling deploys, ElastiCache persistence/HA and the accepted game-state loss window, S3 buckets), and **(3) a secrets & production-observability spec** (Secrets Manager + External Secrets, JWT key handling, per-env config, prod monitoring stack sizing/retention, alert routing, external uptime check). Adding Dependabot + Trivy to the existing CI requirements and inserting a cost/SLO reality check into `platform-operations.md` can be done as edits to existing docs rather than new ones.
