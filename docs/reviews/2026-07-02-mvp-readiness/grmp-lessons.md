## 1. Edge cases / bugs the prototype hit that TurnBase specs miss

**F1 — No room/session reconciliation or stale-state sweep. IMPORTANT.** — **RESOLVED 2026-08-09**: `platform-operations.md` FR-JOB-006…011 and [`room-lifecycle.md`](../../specs/platform/room-lifecycle.md) §5. Three jobs rather than one (their natural intervals differ by four orders of magnitude), and the prototype's startup-cleanup design is **inverted**: with a 5s and a 60s sweep a startup pass is redundant, while a just-booted instance must be *suppressed* for 120s because a recovering system is indistinguishable from a broken one until the Game Host re-registers. The orphaned-participant-row duty is deleted outright in favour of `ON DELETE CASCADE` — a job there is permanent penance for a missing constraint.
Evidence: `/home/hmazur/proj/grmp/ROOM_LIFECYCLE_FIXES.md` — orphaned `room_participants` rows, rooms stuck IN_PROGRESS after service restart, leaked worker sessions; fixed with a startup cleanup service behind a Redisson distributed lock plus deletion of old rooms. `/home/hmazur/proj/grmp/plans/outstanding-issues.md` Issue 5 — stale WAITING rooms accumulated indefinitely (9+ after a few test sessions).
TurnBase checked: `platform-operations.md` FR-JOB-001/002 cover only guest-account and notification cleanup; `game-rooms.md` FR-LIFE-* and `specs/api-design/room-websocket.md` (line 37: pod crash → "clients reconnect via the standard join flow") say nothing about rooms whose clients never reconnect, or In Progress rooms in Postgres whose sessions no longer exist in Redis (Redis *data loss* ≠ Redis *unavailability*, which FR-FAIL-006 covers). A grep across all TurnBase docs for stale/orphan/cleanup/TTL confirms zero coverage.
Suggested change: add an FR-JOB entry (ShedLock per existing FR-JOB-005) for a periodic reconciliation sweep: close Lobby rooms with zero connected participants past a TTL; verify each In Progress room has a live session (Redis routing entry + Game Host ack) and fail it back to Lobby/Closed otherwise; delete orphaned Redis session artifacts for closed rooms.

**F2 — Room closure mid-game doesn't spec game-session teardown or ordering. IMPORTANT.** — **RESOLVED 2026-08-09**: [ADR-0010](../../decisions/0010-session-teardown-ordering.md), `game-rooms.md` FR-XFER-005. **Note the deviation from the suggested fix.** GRMP's own remedy — terminate *before* persisting closure — solves a problem TurnBase does not have: its leak came from `DELETE`ing the room record and losing the reference, and TurnBase never deletes the row. Copying the ordering would make closure block on a hangable remote call and would still have no answer for a teardown that simply fails. Instead the owed teardown is a **durable row keyed by `sessionId`** committed with the state change, and ordering stops being the mechanism. Keying it by session rather than by room is what extends the fix to **normal game end** — the most frequent detach path, which §10 was tearing down with no crash-safety at all.
Evidence: `ROOM_LIFECYCLE_FIXES.md` root cause #3 — worker session terminated *after* room deletion leaked sessions; the fix pinned ordering (terminate session → broadcast → delete DB record, best-effort error handling).
TurnBase checked: `game-rooms.md` FR-XFER-002 closes a room immediately when the host leaves with no humans remaining — including In Progress — but nothing requires calling `TerminateSession`. `specs/internal-grpc/orchestration-gamehost-protocol.md` maps `TerminateSession` only to FR-SESS-005 (game_over) and FR-FAIL-005 (retry limit); the room-closure → session-teardown direction is unspecced.
Suggested change: add a requirement that closing a room with an active session triggers `TerminateSession` best-effort before closure is persisted, and that teardown failure never blocks room closure (the F1 sweep is the safety net).

**F3 — Grace-period timers have no specified home or restart durability. IMPORTANT.** — **RESOLVED 2026-08-09**: [ADR-0009](../../decisions/0009-grace-deadline-durability.md) (deadlines), [ADR-0008](../../decisions/0008-room-ownership-lifecycle.md) (the pod-crash semantics this finding also asked for). Deadlines are absolute timestamps in Postgres computed with the database clock, and the sweep is the **sole** driver — no in-process timer at all, since two mechanisms enforcing one deadline means a dual write and a three-way race on every reconnect. Pod-crash semantics landed differently from the suggestion: rather than a detector reassigning orphaned rooms, ownership is a lease-gated claim and the claim script *is* the failure detector. Writing this up exposed two live defects the finding did not reach — a rolling deploy would have deleted every Lobby room, and an adopting pod would have re-issued event versions that clients discard silently.
Evidence: GRMP's discovery held forfeit tasks in an in-memory ConcurrentHashMap (`docs/architecture-audit-2025-12-29.md` state table) — lost on restart, a contributor to stuck rooms; `ROOM_LIFECYCLE_FIXES.md` "Future Improvements #3" flags worker-crash handling as unsolved.
TurnBase checked: `reconnection-flow.md` FR-GRACE-*/FR-EXPIRY-* fully define *what* happens but never *where* the timer runs or that it survives failover. Under `room-websocket.md`'s room-affinity model an owning-pod crash drops every connection in its rooms at once — the spec doesn't say whether those players all enter grace periods or who fires expiry when the pod that would schedule it is dead.
Suggested change: spec grace deadlines as absolute expiry timestamps persisted in DB/Redis at disconnect time, enforced by an idempotent scheduled sweep (any instance, ShedLock) rather than in-process timers; define pod-crash semantics (all In Progress players of the crashed pod's rooms treated as disconnected at crash-detection time).

**F4 — State serialization must be round-trip-validated with the exact production serialization config. IMPORTANT.**
Evidence: `plans/testing-game-separation-findings.md` Bug 1 — Seven Wonders Duel state serialized fine inside the platform but failed round-trip in the standalone validator: the validator used a bare `ObjectMapper` (no modules) and the extracted game pom lost `<parameters>true</parameters>`. Two implicit configs drifted the moment the game left the monorepo — exactly the third-party-developer situation TurnBase targets.
TurnBase checked: `game-contracts.md` FR-STATE-002 requires serializable state; `specs/gdk-api/backend-gdk-api.md` says the GDK Host serializes JSON transparently; `game-development-experience.md` FR-HARNESS-002 makes the harness reuse *upload* validation — but no upload or harness check does a state serialization round-trip, and nothing requires the harness to embed the Game Host's actual serialization engine/config. TurnBase already applies this lesson to the manifest (shared `manifest.schema.json`); the serialization engine needs the same treatment.
Suggested change: add an FR-HARNESS/FR-UPLOAD item — serialization smoke test (invoke `onInit`, serialize, deserialize, re-serialize, compare) using one shared serialization component consumed by both harness and Game Host; document constructor/parameter-name requirements for state types in the backend GDK spec.

**F5 — Platform shell: no silent trust/origin fallbacks. IMPORTANT (security).**
Evidence: `plans/outstanding-issues.md` Issues A and C — a missing `trustLevel` field plus a client-side `?? 'TRUSTED'` fallback silently loaded an *untrusted* game same-origin with `allow-same-origin`; and the sandbox origin was baked into the frontend build (`VITE_SANDBOX_ORIGIN` placeholder shipped in the prod image).
TurnBase checked: `specs/gdk-api/frontend-gdk-api.md` covers game-side origin validation well, but the platform-frontend shell spec is explicitly not yet written (TurnBase `STATUS.md`, Next Priorities).
Suggested change: when writing the shell spec, require (a) community game bundles served from a separate origin configured at deploy time, not build time; (b) iframe sandbox without `allow-same-origin`; (c) badge/trust level explicit in the room/session API response with the client failing closed — never defaulting to trusted.

**F6 — Minor spec hardening (all MINOR):**
- *Rate limits per environment.* GRMP's 5/15-min login limit blocked every test session (outstanding-issues Issue 4, manual Redis-key-deletion workaround). TurnBase `specs/api-design/rate-limiting.md` hardcodes all numbers with no configurability statement — add one line making tiers property-configurable, with a CI/e2e profile.
- *Error-shape passthrough.* GRMP Bug 2 — a catch-all `@ExceptionHandler(Exception.class)` converted 403 `ResponseStatusException` into 500 everywhere. TurnBase `error-handling.md` defines the shape; add a testable requirement that any framework-thrown 4xx surfaces with its original status in the documented shape (contract test under FR-CICD).
- *Canonical identifiers.* GRMP Bugs 3/8/10 (gameKey vs gameId vs UUID `id` vs `roomId`) cost a full session of frontend breakage. Worth a one-pass audit that TurnBase REST specs pin exactly one external identifier and name per resource, stating where slug vs UUID is accepted.

## 2. Implemented prototype behaviors missing from TurnBase specs (MVP-relevant)

The reconciliation sweep (F1) is the one implemented prototype behavior (StartupCleanupService + distributed lock) TurnBase genuinely lacks and will need for MVP. Smaller: GRMP's `deploy.sh` registers built games with the platform after the stack is healthy — TurnBase's admin upload (admin-tooling FR-OFF-001) covers the mechanism, but document a *seeding step* for getting Official games into a fresh local stack. Positive confirmation: TurnBase's snapshot-on-subscribe including in-flight grace timers (`room-websocket.md`) matches what GRMP had to retrofit.

## 3. Architecture / deployment lessons

**The prototype never reached Kubernetes.** After ~15 months and six phases, GRMP shipped and stayed on docker-compose (6 containers) + nginx + a 250-line `deploy.sh`; "Kubernetes & Scaling" remained "planned" to the end (grmp `STATUS.md`). TurnBase assumes K8s as a constraint (`platform-architecture.md` CON-008, `platform-operations.md` CON-011) plus gVisor as a Must (FR-SEC-001, CON-003). Two IMPORTANT concerns for the MVP path:
- **gVisor won't run in the stated local environment.** Dev is WSL2/Docker Desktop, where `runsc` is effectively unavailable. Spec gVisor as production-only with a documented local fallback (runc + Truffle isolation layer alone) so local dev isn't blocked.
- **Spec a compose-first MVP profile explicitly.** Monolith + Game Host + Postgres + Redis + Grafana is a natural compose target (FR-CICD-004/CON-010 already use compose for tests); treat FR-SCALE-* (HPA, scale-in draining, cold-start budgets) as post-MVP so K8s work can't stall a demonstrable platform the way it stalled GRMP.

Also validated: GRMP's two-service split produced the duplicate-WebSocket/duplicate-event bug class that took a 992-line plan to untangle (`plans/websocket-connection-deduplication-plan.md` — two servers broadcasting PLAYER_DISCONNECTED on the same topic, two room connections per player). TurnBase's monolith-with-single-WebSocket-Gateway decision eliminates that class by construction — worth defending if ever questioned.

## 4. Things the prototype proved hard that TurnBase assumes will be easy

- **Sandboxed guest execution. IMPORTANT.** GRMP's "Tier 2" ambition ended as Chicory Wasm with a fresh instance per call — far short of TurnBase's Espresso-in-Truffle-in-gVisor design — and even trivial `URLClassLoader` loading generated a full bug-fixing phase. TurnBase NFR-PERF-001 (<3s context creation) and FR-SCALE-007 (5s cold start incl. GraalVM init, a **Must**) are unvalidated; Espresso first-context startup is known slow. OQ-001 already calls for the benchmark — run it *before* freezing these NFRs, and keep the OQ-002 fallback (process-level isolation with standard JVMs) a first-class spec alternative.
- **The complex game finds the contract gaps. IMPORTANT.** GRMP postponed Seven Wonders Duel repeatedly; when the validator finally ran, SWD surfaced the serialization gap, the enum-map-key gap, and the spectator/hidden-information design flaw (findings Bugs 1, 9) — things tic-tac-toe could never reveal. TurnBase's effects-push model already fixes the spectator leak by design (FR-FE-006: spectators get broadcast only; no `getStateForObserver` to forget to override), but the meta-lesson stands: build one hidden-information, multi-team reference game against the GDK *early* as contract validation, not last.
- **Filesystem artifact plumbing. MINOR.** GRMP Bugs 4 and 6 (container-UID permissions on bind mounts; `Files.move(ATOMIC_MOVE)` failing across mount boundaries during trust promotion) are designed away by TurnBase's Artifact Store abstraction and metadata-only badge transitions — just ensure the local-filesystem backend never assumes atomic cross-directory moves.

**Already absorbed well:** spectator support as game-declared capability metadata (game-rooms CON-004 vs GRMP Bug 9); uploads private-by-default with explicit review queue (admin-tooling vs GRMP Bug 5 ambiguity); manual host-driven start (FR-HOST-009, matching GRMP finding 11 that auto-start was a mistake); lobby disconnect = immediate leave (FR-DC-002), structurally preventing stale-room accumulation in the happy path; hidden-information safety by protocol design rather than developer discipline.

## Top 3 lessons

First, *lifecycle hygiene is where the prototype bled*: TurnBase needs a specced reconciliation sweep (stale rooms, orphaned Redis session state, In Progress rooms with no live session) and durable, sweep-enforced grace-period timers, because GRMP proved that in-memory timers and inline cleanup reliably leave zombies after any crash or restart. Second, *anything validated outside the runtime must share the runtime's exact artifacts*: GRMP's game passed in-platform and failed standalone purely from drifted serialization config — extend TurnBase's shared-manifest-schema pattern to a shared serialization component used by Game Host, upload pipeline, and test harness alike. Third, *deployment realism*: the prototype never escaped docker-compose in 15 months, so TurnBase should spec a compose-first MVP profile, make gVisor production-only (it won't run on the WSL2 dev machine), and benchmark Espresso context creation before treating the 3s/5s startup numbers as Musts.
